# 三人团队的一次交付模拟

日期：2026-10-01｜对应：[平台设计方案](./AI辅助DevOps平台设计方案.md)

**本文是虚构演练。** 人物、对话、变更、PR、提交、测试结果、环境及发布记录全部为模拟数据；没有创建真实 PR、执行样例测试、合并代码或部署环境。示例工程只提供业务和资源形态背景，不表示其中已确认存在本剧本的缺陷。流程设计沿用主方案，本文不是 Gartner 案例或研究结论。

## 1. 开场：团队、任务与工具

| 人物 | 日常职责 | 本次负责 |
| --- | --- | --- |
| 小林 | 项目负责人，同时负责业务 | 确认需求与设计、合并、生产放行 |
| 小周 | 开发，同时写测试 | 在外部 Phoenix 开发环境实现、提 PR、修复、执行发布 |
| 小陈 | 开发，同时承担交叉复核 | 审 PR、检查测试证据、业务验收 |

这三个称呼是分工，不是新增三个专职岗位。只有两人时，小林兼任小陈的职责，小周仍不独自审批自己的变更。

本次按 PDF 第 6 页的“建立平台团队”要求设置一个轻量责任：小林兼任平台试点负责人，负责 AI 工具选择、项目规则和试点记录；小周负责外部开发工具接入；小陈负责 AI 输出的安全与质量复核。这是三人团队中的职责分配，不新增组织岗位。

本次需求：**知识库问答没有检索命中时，直接返回明确提示，不调用大模型。** 暂不涉及业务前端重建、检索算法改造或数据库迁移。

操作发生在三个地方：

- **DevOps 工作台**：项目、需求与设计、AI 分析、测试证据、发布计划和版本记录。
- **外部 Phoenix 开发环境**：实际修改应用资源、调试和编写测试。
- **Gitee**：真实落地时负责 PR、人工审查意见和合并；本次只演示对应记录。

采用 MVP 路径：成员手动关联 PR，工作台通过已配置连接刷新状态；发布使用官方工具人工执行并回传证据。**本剧本假设已经在接入实验中验证：官方包可以跨 test/prod 使用、能核验部署版本、应用入口测试可运行。** 这些是演练前提，仍不代表已验证 Phoenix 的产品接口。

本次被登记为一个低风险 AI 原生开发试点：AI 参与计划、开发、测试、审查、发布准备和配置材料生成；人确认需求、代码、证据和生产放行。项目规则同时声明不得把密钥、生产数据和生产凭证交给外部 AI 工具。

为便于阅读，用符号代替长摘要：`B0` 为原主分支提交，`H1/H2` 为 PR 两次提交，`M1` 为最终合并提交；`P0/P1` 为旧/新制品摘要。这些不是实际 SHA 或文件。

## 2. 逐步演练

### 第 1 步：小林创建项目

**位置：工作台 → 新建项目 → 组装模板。**

小林选择基础模板“Phoenix 资源型项目”，团队模式选“现有团队接入”，应用交付策略选“小团队、人工审查、人工生产发布”。他勾选项目基线、`AGENTS.md`、需求澄清 Skill、PR 审查 Skill、工作区术语表/架构说明/测试指南、PR 模板、`test`/`prod` 环境定义和发布运行手册。模板只带入配置占位符，不包含环境密钥。

小林填写项目名“内部知识库”、示例仓库关联、项目目标和团队成员，主分支设为仓库实际使用的 `master`。平台扫描现有仓库后发现它已有测试目录和项目说明，没有同路径 `AGENTS.md`；文件预览标记为“新增”，已有文件标记为“保留”，没有覆盖项。平台也提示 Phoenix 资源型模板的文件发现路径需要和当前外部 AI 开发平台适配；本演练假设团队已确认映射规则，不代表已验证某个真实产品接口。

小林预览变量渲染后的文件树、环境差异和拟启用动作。密钥/令牌扫描无命中，生产发布权限未被模板授予。由于仓库已有内容，平台生成初始化分支和 `TPL-001 v1` 初始化 PR；小林确认后按日常 PR 流程审查并合入，模板实例记录模板版本、参数摘要、文件清单和冲突处理结果。

如果这套组件还要用于后续项目，小林可以选择“保存为团队模板”。平台先去除项目名称、客户生产数据、密钥和令牌，把组件清单、变量定义、适配器映射和风险策略保存为草稿；项目成员审阅后发布 `TPL-PHX-TEAM v1`。未审阅的模板草稿不能直接用于其他项目。

> 小林：先管好这一套知识库，需求、测试和上线记录都在这里。
>
> AI：已整理工程概览。当前有服务端资源与反推规格，现有 25 个测试定义访问的是 ikkyu 后端。Phoenix 用户入口和本次问答行为需要单独验证。

小林登记 `test`、`prod` 两个环境及凭证引用。演练假设两个环境原本都运行 `v0.1 / B0 / P0`，这一步是在新工作台登记已有项目，不是从零开发整个知识库。

平台同时记录三项试点设置：使用现有外部 AI 开发平台；启用 AI 代码审查和合规检查；从这个低风险变更开始观察交付效率与遗漏情况。小林和小陈完成一次简短的使用约定确认，明确提示词中不得放入密钥，AI 输出必须经过人和可重复检查验证。

**平台结果：** 项目已创建并记录 `TPL-001 v1` 实例，成员、环境和项目工作区文件已登记；尚无业务变更。不会把“发现 25 个测试”显示成“25 个测试已通过”。

如果这是新成立团队，小林会选择“新团队引导”：平台逐个解释生成文件用途和 Skill 触发场景，默认开启人工审查并关闭生产自动动作。若团队已有成熟习惯，则走本次的增量接入路径，只补缺失文件；两种模式都不因团队熟练程度而跳过生产风险确认。

| 团队类型 | 模板方式 | 默认行为 |
| --- | --- | --- |
| 新团队 | 引导式组装 | 少量必填项；解释每个文件和 Skill 的用途；默认人工审查、关闭生产自动动作；用低风险变更完成第一次训练 |
| 现有团队 | 扫描并增量接入 | 先识别已有指令、Skill、PR 模板和测试入口；只补缺失内容；冲突进入比较视图；保留原有分支、测试和发布习惯 |
| 熟练团队 | 快捷模板 | 可使用最近模板、批量创建和低风险自动检查；生产发布、数据迁移和权限变更仍需确认 |

这三种模式共用同一套模板版本、变量校验、敏感信息检查、diff 和撤销机制；团队模式只改变引导和默认动作，不改变权限边界。

### 第 2 步：小林输入需求，AI 补成可验收内容

**位置：工作台 → 变更 → 新建。**

> 小林：没查到资料的时候，别让模型凭空回答，直接告诉员工没找到。
>
> AI：需要区分“检索成功但没有命中”和“检索服务故障”。前者提示无资料；后者仍提示服务异常。是否继续保留命中时的问答和现有权限校验？
>
> 小林：是。无资料时就显示“没有找到可用资料，请换个问题或联系管理员补充。”

AI 形成 `CHG-001`：**问答无命中时返回提示并跳过模型调用**，负责人小周，交付目标生产上线。

| 验收编号 | 预期 | 所需证据 |
| --- | --- | --- |
| AC-01 | 有权用户检索成功且命中为 `[]` 时返回固定提示，模型调用次数为 0 | Phoenix 入口测试及测试模型的调用计数 |
| AC-02 | 有命中时保留原问答链路 | 测试夹具命中记录、模型调用与结果断言 |
| AC-03 | 无权用户不能读取受限内容 | 不同角色的拒绝路径断言，模型调用次数为 0 |
| AC-04 | 上游检索故障不会被显示为“没有找到资料” | 受控故障注入和错误语义断言 |

这些不是四张测试工单，而是同一变更里的四行验收标准。测试通过后再生成对应报告引用。

AI 还生成计划附件 `TM-001`：本次只读检索结果分支，不新增权限边界、外部接口、配置密钥或数据迁移；风险级别为低。该附件是威胁建模草稿，不是安全认证结论，需由小陈确认。

**平台结果：** `CHG-001 = 收件箱`，需求草稿可编辑。

### 第 3 步：AI 出短设计，小林一次确认

**位置：同一变更 → 方案。**

> AI：在 `ask` 的检索完成之后、提示词组装和模型调用之前增加空集合分支。先校验权限，确认检索成功后才判断命中数量；故障保留原错误路径。无需数据库迁移。
>
> 小陈：测试里必须观察“没有调用模型”，只断言提示文字不够。
>
> 小林：按这个范围做。

小陈同时核对 `TM-001` 的四项检查：权限校验仍在检索前、无新增外部调用、无密钥进入变更、无数据库迁移。AI 生成的威胁清单和安全检查结果作为设计附件保存；本次不启用自动修复或自动响应。

平台记录 `需求 v1 + 设计 v1` 和确认人，生成开发上下文包。包里有四条验收、基线 `B0`、相关资源、命名约定、测试方式和不改动范围，不携带密钥。

**平台结果：** `收件箱 → 就绪`。第一次人工确认完成。

### 第 4 步：小周到外部开发环境工作

**位置：外部 Phoenix 开发环境。**

小周建立短分支 `chg-001-empty-answer`，把上下文包交给开发 AI。

> 小周：按 CHG-001 的已确认方案实现，先补空结果用例，不修改检索算法和数据结构。

开发 AI 生成资源修改与测试草稿，小周检查后提交 `H1`。为了展示审查价值，**本剧本特意假设 H1 留下了一个遗漏：只判断结果是否为空值，没有判断集合长度为 0。** 这是假设的修改内容，不是对原仓库的缺陷认定。

开发 AI 同时给出资源差异解释、调试建议和测试补丁；重构建议由小周人工取舍。由于本次没有新增或修改 API，API 定义和文档任务标记为“不适用”，不伪造接口变更。

**平台结果：** 小周选择“开始开发”，`就绪 → 开发中`；工作台只关联外部开发活动，不提供第二个 IDE。

### 第 5 步：小周提 PR

**位置：Gitee → 创建 PR；工作台 → 关联 PR。**

AI 根据变更和实际差异准备 PR 草稿，小周检查并提交。演示 PR 编号为 `#12`：

```text
标题：[CHG-001] 问答无命中时返回提示并跳过模型调用

目标分支：master（B0）
来源分支：chg-001-empty-answer（H1）

问题：没有匹配资料时仍可能进入模型回答链路。
改动：在问答逻辑中增加无命中提示分支，新增 4 项应用验收测试。
范围：不修改检索算法、数据库结构和有命中时的问答行为。
关联：CHG-001 / 需求 v1 / 设计 v1
验证：待共享测试环境执行；本地调试不代替发布验收。
```

小周在工作台关联 `#12`，平台核对实际 base/head、需求版本和差异。AI 草稿本身不对外发送；PR 由小周提交。

**平台结果：** `开发中 → 待验收`；`PR #12 = 待审查 / H1`。提 PR 不代表已完成。

### 第 6 步：AI 审查与测试并行，发现遗漏

**位置：工作台 → 测试与审查；执行发生在隔离测试环境。**

在演练中，成员将 H1 的预览包部署到隔离验证目标，执行器产出两份报告：

- 外部后端契约测试：**25/25 通过（模拟）**，只说明该后端契约测试集通过。
- Phoenix 应用验收测试：**3/4 通过（模拟）**；AC-01 失败：返回 `[]` 时仍调用模型 1 次。
- AI 代码/安全检查：**建议通过（模拟）**；未发现新增权限、外部接口、密钥或数据迁移，但该结果不能替代人工审查。

AI 的问题卡：

```text
REV-01：空集合没有进入无资料分支
定位：ask / 检索结果判断节点（模拟语义定位）
依据：H1 只处理空值；TEST-H1 的 AC-01 记录模型调用 1 次。
影响：违反已确认的“无命中时不调用模型”要求。
建议：在检索成功后判断命中数量为 0，并重新验证 AC-01–04。
处置：待人工确认；阻止验收和合并。
```

**平台结果：** `待验收 + 阻塞`；下一步明确分派给小陈：“确认 REV-01，决定是否退回。”平台不会用总计通过率掩盖一个关键用例失败。

### 第 7 步：小陈审 PR，要求修改

**位置：Gitee → PR #12。**

小陈打开原始差异和 TEST-H1，不只读 AI 摘要。

> 小陈：这个问题成立。空结果是 `[]`，当前分支没有覆盖。请补集合长度判断，保留上游错误分支，并给出 Phoenix 入口的复验结果。

小陈提交“要求修改”的审查结论，工作台同步该结果，将发现交回小周。

**平台结果：** `待验收 → 开发中`；`PR = 要求修改 / H1`。AI 提供证据，人工承担正式审查判断；没有额外创建一个“审批工单”。

### 第 8 步：小周修复，同一个 PR 更新到 H2

**位置：外部开发环境 → 提交 → Gitee。**

小周修复结果数量判断，确认错误与无资料路径分开。测试仍是同一套四个验收用例，没有通过改写预期让红灯变绿。推送 `H2` 到同一个 PR。

平台发现 head 变化，TEST-H1 和 H1 的审查保留为历史，不再满足当前 H2 的检查要求。复验结果：外部契约 25/25、应用验收 4/4，均为模拟运行。

> AI：H2 对应的 AC-01 已通过，模型调用次数为 0。REV-01 建议标为已修复，等待小陈复核；旧的审查意见仍可查阅。

**平台结果：** `开发中 → 待验收`；`PR = 待重新审查 / H2`。推送新提交不会自动沿用旧批准或自动消除人工审查结论。

### 第 9 步：小陈批准当前版本的 PR

**位置：Gitee → PR #12；工作台展示关联证据。**

小陈复核 `H1 → H2` 的修复和 `B0 → H2` 的整体差异，查看四条验收证据。

> 小陈：REV-01 已修复。无命中、正常命中、无权限和上游故障四个路径都有证据，批准当前 H2 合入。

**平台结果：** `PR = 已批准 / H2`，主分支仍为 `B0`，变更仍为待验收。PR 批准的含义是允许合入这个差异，不是生产发布许可。

### 第 10 步：小林合 PR

**位置：Gitee → PR #12 → 合并。**

小林看到：当前 head 为 H2、批准有效、必需检查通过、无未解决阻断。合并前再次确认 `master` 仍为 B0。

> 小林：合入这一版。

演练采用 squash merge，形成 `M1`。其应用内容与已审 H2 相同，但提交身份不同。工作台刷新主分支状态，核对 `B0 → M1` 与批准差异相符，启动最终提交的检查。

**平台结果：** `PR = 已合并 / M1`；变更仍为待验收；生产仍运行 `v0.1 / B0 / P0`。合并不会触发未经批准的生产部署。

如果合并前主分支已变，必须更新基线、检查冲突和完整差异、重新运行相关检查并取得对应批准；不能按旧 B0 的结果直接继续。

### 第 11 步：从 M1 生成候选包，发布到 test 验收

**位置：官方发布工具 + 工作台 → 发布与环境。**

小周从干净的 M1 导出候选制品 P1，登记包摘要、源提交和导出工具信息，创建 `REL-002 / v0.2`。平台比对 test 当前 B0 到 M1 的全部差异，确认仅包含 CHG-001。

按本次人工模式，小周使用官方工具把 P1 发布到 test，回传制品证据；小陈核验目标版本与配置 `T1`。然后执行最终版本检查：

- M1 的资源检查通过（模拟）。
- 外部契约测试 25/25 通过（模拟，记录后端目标身份）。
- P1 + T1 的应用验收 4/4 通过（模拟，记录角色与模型调用计数）。
- 配置检查 `CFG-002` 与运行手册 `RUN-002` 已由小陈复核（模拟）。
- 小陈确认用户提示与错误路径符合需求 v1。

**平台结果：** `test = v0.2 / M1 / P1 / 已核验`，`REL-002 = 可申请生产发布`。H2 的绿色结果保留为开发验证历史，不替代这次制品验收。

### 第 12 步：小林确认生产发布计划

**位置：工作台 → REL-002 → 生产发布。**

AI 汇总发布摘要，平台的确定性检查验证范围和证据：

```text
目标：prod
当前：v0.1 / B0 / P0
候选：v0.2 / M1 / P1
本次变更：CHG-001，无额外未关联改动
配置：沿用已登记的生产配置 C1；应用配置无新增项
验证：P1 已通过 test / T1 的验收；生产配置差异与连接预检通过
数据：无数据库迁移，不覆盖业务数据
恢复：回退到 P0，保留相容配置 C1；旧包恢复流程已演练
生产检查：版本核验、正常问答与无资料提示的无破坏性冒烟
执行人：小周；放行人：小林
```

> 小林：确认发布这个 P1 到 prod。

批准绑定 `M1 + P1 + prod + C1 + 本次验收证据`，平台生成部署记录 `DEP-002`。这不授权把换过的包或配置继续发出去。

**平台结果：** `DEP-002 = 已批准 / 待人工操作`。如果小周此时更换包，或任何人修改 C1，批准立即过期，必须重新预检和放行。

### 第 13 步：小周执行生产发布，平台等待核验

**位置：官方发布工具；工作台记录进度。**

平台重新核对 prod 仍是 B0/P0/C1，锁定该项目的生产发布入口。小周按 DEP-002 的操作单发布 P1，回传操作与包证据。

> 小周：官方工具显示发布完成。
>
> 工作台：执行回执已收到，正在核对实际版本和冒烟结果。

此时部署状态是**验证中**，不是成功。小陈按已验证的版本核验方法检查实际 P1，执行受控的生产冒烟；不在生产跑带新增、删除和清理操作的整套后端契约测试。

**平台结果：** `PR 已合并`、`DEP-002 验证中`、`CHG-001 待验收`。发布协调锁约束工作台流程；拥有外部工具权限的人仍可能绕开工作台，因此人工模式还需要约定不并行发布，并在前后核验目标状态。

若此时超时，记录“状态未知”，先核对目标版本和官方操作结果，不自动重复执行导入或把超时当作回滚触发器。

### 第 14 步：实际版本和冒烟通过，关闭变更

**位置：工作台 → 发布结果与项目概览。**

演练结果：实际版本匹配 P1，生产配置仍为 C1，无破坏性冒烟通过。平台将 DEP-002 标记成功，释放发布锁。

> AI：v0.2 已完成验证。CHG-001 达到“生产上线”交付目标，发布说明和验收证据已关联。

小林看到：

```text

CHG-001：已完成
PR #12：已合并 → M1
test：v0.2 / P1
prod：v0.2 / P1 / 已核验
完整记录：需求 v1 → 设计 v1 → PR #12 → M1 → P1 → DEP-002
历史保留：H1 的失败、REV-01 的处置、H2 的复验与人工审查
```

这次没有新增工时统计、迭代会议或日报。AI 可以生成交付摘要，团队只在需要时使用。

平台同时关闭试点记录 `PILOT-001`：保留需求、AI 输出、H1 失败、人工审查、H2 修复、测试和发布证据；人工协调耗时、返工次数和缺陷结果进入待后续真实试点填写的指标表，不虚构提效比例。三名成员在结束时确认一次“哪些 AI 输出可直接采用、哪些必须保留人工复核”，作为下一次变更的团队能力改进输入。

## 5. 人实际需要做什么

- 小林：填一次项目设置；确认一次需求/短设计；合并一次 PR；批准一个明确的生产计划。
- 小周：在现有开发环境实现和修复；提一个 PR 并关联；按人工接入方式执行 test/prod 发布和回传。
- 小陈：确认 AI 提出的问题，要求修改；复核修复并批准 PR；核对最终制品验收与生产结果。
- AI：整理背景与验收、准备上下文、生成 PR 草稿、分析资源差异、对照失败证据、汇总验收与发布材料。
- 平台/执行器：校验版本、执行已登记测试、记录真实结果、使过期证据失效、核对批准范围、协调发布状态。它们不是模型的自由判断。

这次模拟中，AI 的价值集中在减少重复组织材料和帮助发现遗漏；人工注意力留给范围、正确性和生产影响。后续接通可靠的官方发布 API 后，小周的手工发布步骤可交给执行器，其余验收规则保持不变。

## 6. 三个异常分支

| 事件 | 工作台应怎样处理 | 人下一步做什么 |
| --- | --- | --- |
| 审 PR 后又推了新提交 | 旧批准不覆盖新 head，相关检查过期 | 复验并重新审查；不让作者自己恢复批准 |
| 生产批准后更换配置 | 已批准计划过期，尚未启动的部署停止 | 查看配置差异，补必要验证并重新批准 |
| 发布超时但不知道是否生效 | 保持状态未知，禁止盲目重试有副作用的步骤 | 查询目标与操作记录；确认后继续验证或按计划恢复 |
| 生产冒烟失败或监视器发现异常 | 生成 `RCA-001` 根因假设、影响范围和响应草稿；不自动修改生产 | 小陈确认事实，小林决定回滚、修复或继续观察；形成新的变更记录 |

这些分支与主方案的控制要求一致。本次只模拟正常发布成功，**没有执行真实回滚，也没有验证任何真实平台的自动化能力**。

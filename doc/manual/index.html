01 / 一次启动，进入工作台

docker compose up -d --build

容器自动初始化 MySQL、Gitea、统一管理员、OAuth、备份计划和第一份完整冷备。启动页在完成前显示准备状态。容器健康后打开 http://localhost:8080。

使用内置账号 admin/admin 登录。平台仅支持用户名密码，不支持 Passkey/WebAuthn。继续使用默认密码时，工作台每次登录都会提示修改密码；可以选择“本次忽略”。成功修改密码后不再提示。

只需一个容器和两个 named volume：data 保存数据库、仓库、配置、密钥、日志；backup 保存全量归档。删除容器不等于删除数据卷。

首次指定其他端口时同时设置 DEVOPS_PORT 和 PUBLIC_ORIGIN。已有卷保存的地址不会随默认环境值改变。外部访问使用 HTTPS 入口，Gitea 和 MySQL 不对外开放。

02 / 一个账号，明确的职责

人类

提出目标、审证据、签发 Gate、合并和处理未知结果。

DevOps agent

维护方案、说明书、接口契约、API/E2E 场景与测试数据说明。

IDE agent

实现已确认目标，维护代码与单元/组件测试，发起受控执行请求。

平台管理员在「项目与授权」创建统一账号，再设置项目负责人、审查人、成员或观察者。账号在 Gitea 创建，DevOps 不保存第二套人类密码。

IDE Git 凭证与 agent 委托由已登录的人类账号签发，限定项目，有效期一小时，可随时撤销。IDE 预设逻辑和隔离 Runner 使用独立能力及 Ed25519 公钥；他们只能提交执行证明，不能签 Gate。

03 / 从一个清晰目标开始

  1. 创建项目，填写仓库标识、发布环境、隔离验收环境、固定工具版本、API/E2E 命令 ID 和 Runner 名称。
  2. 创建 Intent，描述背景和可观察结果，选择类型与风险。生产热修复还需要事件编号和已确认生产版本。
  3. 编辑点方案：目标、范围、非目标、风险、责任人、参考与采纳。
  4. 编辑应用方案：改变对象、权限、前置条件、不变量、验收、幂等、事务与恢复。纯代码变化明确写无持久状态改变。
  5. 审阅 Gate A，确认当前方案和基线，填写理由。程序创建实际工作分支和不可变工作区快照。

表单可人工填写；「结构化导入」适合粘贴 agent 生成的合规草稿。可选模型未配置时会明确提示，不会伪造方案或执行结果。

04 / 三个决定点

目标 → Gate A（方案确认）→ 开发与证据 → Gate B（交付候选确认）→ PR 与组合 → Gate C（发布确认）→ 实际结果

GATE A · 方案确认

签发目标并创建工作区

确认目标和允许的状态改变，不审批实现。IDE 只能向这个已确认分支推送范围内文件。目标、基线或控制配置改变，需要新的确认。

GATE B · 交付候选确认

签发交付并创建 PR

审真实代码差异、说明书、变更说明和接口契约。同一来源提交须有构建以及 unit、component、security、API、E2E 的通过证据。用例已生成或操作已登记都不算通过。

程序自动创建真实 PR。人类进入独立合并页逐个确认；目标分支改变后，其余 PR 需要重新检查并签发 Gate B。

GATE C · 发布确认

签发发布输入

对最终合并 SHA 重新构建和验收，填写系统方案。生产基线、制品、配置、应用方案集合、环境、迁移、健康和恢复必须一致。高风险由另一位审查人会签后，负责人最终签发。

平台只签发输入。IDE agent 请求发布，IDE 预设逻辑部署同一制品并报告实际版本。版本、制品、环境和健康全部匹配才核验关闭。

每道 Gate 都按「差异与缺口 → 固定对象 → 理由确认」操作。看见 STALE、UNKNOWN 或缺口时先处理原因；输入在确认瞬间变化会被拒绝。

05 / 两个 agent，共享一个工作区

从「项目与授权」复制 Git 唯一入口，形如 http://localhost:8080/git/project.git。Git 的账号为统一用户名，密码为 DevOps 短时 Git 凭证。用 IDE 的安全凭证管理器保存，不要在远端 URL 中嵌入令牌。

在已确认的任务工作树内运行本仓库的 workspace 客户端：

# 通过安全环境配置 DEVOPS_URL、DEVOPS_PROJECT、DEVOPS_TOKEN
node /path/to/ai-devops/cli/devops.mjs workspace init
node /path/to/ai-devops/cli/devops.mjs workspace sync

双方先读根目录 agent.md。正式方案与代码在业务分支；请求、快照和回执在 .devops/，由受保护的同仓控制分支提供。两个 agent 通过 outbox 请求和 inbox/receipt 交接，不需要互相调用模型。

文件不能签发 Gate、合并或改权限。禁止创建/删除远端分支、强推、直推主线、改锁定方案。只读投影若被修改，客户端会停止覆盖，先保留本地改动，再重新拉取。

执行端接入、签名原文与完整动作字段见 执行端接口约定。平台不接收生产发布密钥，不执行用户项目脚本。

06 / 未知结果，先对账

STALE · 已失效

提交或输入发生变化。按当前版本重新构建、验收或签发。

UNKNOWN · 未知

操作可能已发生。保持原 operation ID，查询 Git 或由原执行端补交签名实际结果。

FAIL_CLOSED · 阻断

实际版本或授权严重不符。核验事实后记录恢复理由，重新验收。

在「发布与运行」打开操作详情。可确定核验的 Git 操作由程序查询；测试、构建、发布需要原执行身份的证明。进入 HUMAN_RECOVERY 后由人类选择恢复。不要通过新建请求键重发未知合并或发布。

生产热修复从实际确认版本起步，发布后显示同步任务。同步回功能线也要走方案、证据、PR 和人工合并；不能把同步当第二次生产发布。

07 / 备份与恢复

默认每日 03:00（Asia/Shanghai）全量冷备，在「系统运维」可修改计划或立即备份。备份先暂停入口、排空请求，依次停止业务和数据库，再完整归档 data。完成后自动恢复服务。

保留最近 7 个每日恢复点、4 周每周一个恢复点和最近一次升级前恢复点。归档校验完成和实际恢复演练是不同状态。恢复点取决于最近成功备份；backup 与 data 在同一主机时，另行复制归档到异地。

docker compose exec devops devopsctl backup

还原到新卷

选定备份 ID 和相同版本镜像。正式恢复先停止旧服务，保留旧卷；以下示例先还原到全新 data 卷，backup 在恢复命令中只读：

docker volume create devops-restored-data
docker run --rm --entrypoint devopsctl \
  -v devops-restored-data:/data \
  -v ai-native-devops_backup:/backup:ro \
  ai-native-devops:local restore <backupId>

演练不发布端口，不开放人类登录或执行派发：

docker run -d --name devops-restore-drill \
  -e DEVOPS_RESTORE_DRILL=1 \
  -v devops-restored-data:/data \
  -v ai-native-devops_backup:/backup \
  ai-native-devops:local
docker exec devops-restore-drill cat /data/ops/status.json

恢复校验包括 MySQL、审计链、Git 对象与引用。旧浏览器会话和委托撤销，生产基线重新确认，未完成操作暂停对账。恢复演练报告在目标 data 卷，测试报告可另行导出。

正式使用恢复卷前停止演练容器，再以同版本镜像挂载该卷和 backup 启动普通实例；采用原保存的域名/端口。不能直接覆盖非空 data，也不能把降级镜像接到新版本 datadir。

08 / 以执行记录为准

当前已提供可运行的控制面与单容器部署，仍需接入你的真实 IDE 控制面和 Runner。测试中的发布执行器只模拟隔离环境，不代表用户生产系统已经上线。

详细的已实现能力、尚未完成的升级/故障矩阵/数据模型项见 实现与验收范围，本次执行证据见 验证记录。

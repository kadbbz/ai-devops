三层影响面

先看现状，再看规格，最后看建议

仓库当前规格定义建议变化

页面 · Page

影响是契约兼容与后续补建，不把规格页面当成已存在页面。

01
仓库当前

页面资源有限

PC 资源可确认有“页面1”和系统页；前端设计文档标记本轮暂不涉及管理端页面。

证据：spec/01-前端设计.md · documents/page/PC
规格定义

问答与检索页契约

kb-qa 调用 KB_GetAvailableDomains、ask；kb-search 调用领域列表与带权限检索，结果使用 markdown / results。

证据：前端设计规格 §2–3
建议变化

页面结构保持不变

若后续补建问答页，只消费既有 markdown 返回值；无命中提示由服务端统一返回，页面只展示，不复制判断逻辑。

实施：先补入口验收，再决定页面重建范围

逻辑 · Logic

主影响面在 ask 的检索成功分支与 LLM 调用之间。

02
仓库当前

已有权限与检索链路

先取可用领域，再校验访问权限；通过后调用 KB-RetrieveKnowledgeWithPermission，拼接命中文本并调用“大模型对话”。

证据：documents/logic/.../ask.json diagram
仓库当前

现有异常语义

无权限已有固定提示；大模型无候选回答也有后置处理。未看到“检索成功但 results 为空时短路”的已确认分支。

结论来自静态流程核对，未执行运行时验证
建议变化

增加空集合判断

在检索成功后、拼接提示词前判断知识列表长度为 0：返回固定 Markdown，模型调用次数为 0；有命中继续原路径。

边界：不改权限、检索算法、输入输出契约

数据 · Data

本次候选变更没有足够证据支持新增业务表。

03
仓库当前

本地数据库是流程引擎表

app.phxdb 可见 ACT_*、FLW_* 等流程引擎表；知识内容与检索数据由外部 ikkyu API / 存储提供。

证据：database/app.phxdb · spec/README.md
规格定义

数据契约已有边界

检索返回“检索命中”列表及耗时字段；问答只返回字符串 markdown，调用方不直连知识库服务。

证据：ask.json returnValues · 前端设计规格 §1
建议变化

不新增表结构

只增加逻辑分支和测试证据。发布前记录变更影响分析，明确“无迁移、无数据覆盖”；若未来要存提示文案，再单独立项。

实施：数据库迁移检查项应为 N/A，并留证

建议逻辑变化

把控制点放在检索成功之后、提示词组装之前

实施做法 · 轻量四步

  • 1 / 先锁基线：保存 ask.json、相关依赖和当前测试盘点；确认不是从规格推断运行事实。
  • 2 / 改一个分支：只在检索成功后增加空集合判断；固定提示放在服务端，避免多个页面产生不同文案。
  • 3 / 补四类证据：无命中且不调用模型、有命中保留回答、无权限不泄露、检索故障不伪装成无资料。
  • 4 / 发布留证：确认无数据库迁移；分别核验测试制品、环境配置与应用入口，再决定是否补建页面。

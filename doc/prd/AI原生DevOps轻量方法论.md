# AI 原生软件工程轻量方法论

适用对象：小团队、单仓库或少量仓库、低到中等风险的软件变更。

本方法把 AI 软件工程分为两个确定性控制面、两个受控 agent 和一个责任主体：

- **DevOps 预设逻辑（程序）**控制目标、交接、审批、证据、分支和 PR 状态。
- **DevOps agent**负责理解需求、整理材料、维护文档和 API/E2E 验收。
- **IDE 预设逻辑（程序）**控制编译、制品、部署、发布、健康检查和回滚。
- **IDE agent**负责代码实现、单元/组件级验证，以及提交编译和发布请求。
- **人类**负责确认目标、审查证据、签发、合并和处理例外。

DevOps 不参与部署执行，不调用基础设施 API，不持有部署凭证。IDE agent 不能绕过 IDE 预设逻辑直接编译、发布或操作基础设施。

## 1. 核心原则

1. **生成不等于授权。** agent 可以生成草稿、代码、测试和建议，但不能自行签发、合并、改变权威状态或发布。
2. **程序决定能否继续。** 权限、状态、版本、证据、分支血缘和发布条件由确定性程序判定，不能由自然语言解释替代。
3. **人类承担关键决策。** 人类确认目标和状态改变，审查证据并签发交付；高风险和未知结果必须由人类决定。
4. **编译和发布严格程序化。** IDE agent 只能提交请求和读取结果；IDE 预设逻辑执行固定编译、制品生成、部署、发布、健康检查和回滚。
5. **证据绑定精确版本。** 证据和批准同时绑定方案版本、提交、依赖、配置、工具、策略、环境和制品摘要；来源变化后自动失效。
6. **失败默认关闭。** 校验、权限、状态机、指纹、审计或结果对账失败时冻结后续动作，进入人工恢复路径。
7. **不在 DevOps 内设计开发环节。** 代码组织、调试、实现步骤和单元/组件级测试由 IDE 侧完成；DevOps 只接收确认后的任务和结果。

## 2. 三类方案的最小语义

三类方案只作为轻量交接契约，不作为三套独立的开发流程。

| 类型 | 最小定义 | 允许内容 | 权限边界 |
| --- | --- | --- | --- |
| **点方案** | 只读地说明要观察、判断或讨论什么 | 目标、范围、非目标、查询条件、风险、责任人、评审建议和参考资料 | 不改变软件应用数据状态 |
| **应用方案** | 说明如何改变软件应用数据状态 | 写入、更新、删除、迁移、配置或权限变更；前置条件、不变量、验收、幂等和回滚 | 只有人工确认且程序校验通过后才可受控执行 |
| **系统方案** | 说明一组应用方案如何交付 | 最终提交、制品、配置、环境、顺序、健康检查和恢复方式 | 只是 IDE 预设逻辑的发布输入 |

点方案中的“建议、参考”包括人类评审建议、历史复盘、行业规范、设计资料、监控记录、外部链接和 agent 候选意见。它们必须标明来源、适用范围和采纳状态，默认不具备约束力；被人类采纳后，才可进入应用方案或系统方案。

所有方案各自只有一个权威版本，人类视图和 AI 视图由同一版本生成。方案版本、上下文清单和签发结果形成不可变交接快照，IDE agent 只能读取该快照。

## 3. 五方分工

### 3.1 DevOps 预设逻辑（程序）

DevOps 预设逻辑是交接和治理的确定性控制面，负责：

- 校验方案结构、引用关系、风险等级和必填约束；
- 保存权威版本，计算指纹，创建不可变确认工作区；
- 执行状态机、权限、职责分离、审批失效和证据门禁；
- 校验分支血缘、最终提交、组合验证和制品来源；
- 在 Gate B 通过后自动创建 PR，在合并前后执行保护规则；
- 记录审计、操作 ID、异常、未知结果和恢复上下文。

它不生成业务判断，不执行开发、编译、部署或基础设施操作，也不把自然语言直接当成策略。

### 3.2 DevOps agent

DevOps agent 负责理解和验收材料：

- 接收 intent，起草点方案、应用方案和系统方案草案；
- 整理评审建议、参考资料、影响范围、风险、反例和偏离说明；
- 维护说明书、变更说明、接口契约和验收标准；
- 生成、维护和受控执行 API 测试、E2E 测试及其测试数据；
- 汇总测试、文档、状态改变和安全检查证据，解释失败和缺口；
- 在程序允许的 Runner 和环境中执行 API/E2E 测试。

它不能签发、改变权威状态、批准自身输出、直接操作生产工具或调用部署 API。测试执行结果必须由 Runner、环境、命令、日志和测试数据共同证明。

### 3.3 IDE 预设逻辑（程序）

IDE 预设逻辑是工程执行和发布的确定性控制面，负责：

- 固定编译器、依赖解析、锁文件、构建命令和构建环境；
- 校验已确认工作区、系统方案、提交、配置和权限是否匹配；
- 生成、签名和登记制品、来源证明及 SBOM；
- 执行部署策略、环境权限、发布顺序、健康检查和回滚；
- 核对实际版本、制品摘要、操作 ID 和发布结果；
- 拒绝绕过编译、制品、权限、发布和恢复规则的请求。

它不生成业务判断，不修改方案，不接受 agent 直接调用基础设施 API。

### 3.4 IDE agent

IDE agent 聚焦开发和发布请求：

- 读取已确认工作区，在指定分支实现代码；
- 编写和执行单元/组件级测试，修复代码问题；
- 提交编译/制品请求，读取 IDE 预设逻辑返回的结果；
- 提供代码差异、测试日志、构建参数和偏离说明；
- 提交部署/发布请求，读取并解释 IDE 预设逻辑返回的结果；
- 在热修复同步线上准备回合并提交和 PR。

它不能修改已签发目标、维护说明书和 API/E2E 测试的权威版本，不能直接部署、发布或使用长期生产凭证。

### 3.5 人类

人类负责提出和确认目标，审查方案、差异、证据和风险，签发 Gate A/B/C，在 DevOps 中合并多个 PR，处理例外、回滚和未知结果。

人类不能把 AI 自述当证据，也不能在已签发对象被手工修改后继续使用旧批准。

### 3.6 自治等级

| 等级 | 含义 | 本方法的使用方式 |
| --- | --- | --- |
| L1 观察 | 读取、分析、报告事实 | 查询状态、汇总日志、生成诊断 |
| L2 建议 | 生成草稿，不改变权威状态 | 方案、文档、测试、风险和偏离建议 |
| L3 经批准后行动 | 人工批准且程序校验通过后执行 | 隔离开发、受控测试、编译请求、发布请求 |
| L4 自主行动 | 无逐次人工批准执行副作用动作 | 首期禁止合并、生产发布、权限变更和基础设施操作 |

DevOps 和 IDE 预设逻辑不属于 AI 自治等级。所有副作用动作都必须通过对应程序和人工签发。

## 4. 交接和审批

标准路径如下：

```text
intent（需求、缺陷、事件或改进建议）
  -> DevOps agent 生成点方案、应用方案、文档和 API/E2E 用例
  -> 人类审查并签发 Gate A
  -> DevOps 预设逻辑生成确认工作区
  -> IDE agent 开发、执行单元/组件测试并提交编译请求
  -> IDE 预设逻辑编译、生成并登记制品
  -> DevOps agent 更新说明书、变更说明并执行 API/E2E 测试
  -> DevOps 预设逻辑汇总证据
  -> 人类审查并签发 Gate B，程序自动创建 PR
  -> 人类在 DevOps 中合并一个或多个 PR
  -> 程序以最终提交重新验证组合结果
  -> DevOps agent 生成系统方案，人工签发 Gate C
  -> IDE agent 提交发布请求
  -> IDE 预设逻辑部署、发布、健康检查或回滚
  -> 程序记录实际结果并关闭或转入异常流程
```

### Gate A：目标和状态改变确认

人类确认：

- 点方案的目标、范围、非目标、建议与参考、风险和责任人；
- 应用方案的状态改变范围、前置条件、不变量、验收、文档更新、API/E2E 用例和恢复方式；
- 仓库、分支基线、数据分级、目标环境、禁止操作和上下文清单。

Gate A 只确认“观察什么、改变什么、什么算完成”，不批准 AI 的实现细节。

### Gate B：交付签发

人类审查：

- 最终代码差异、提交和分支血缘；
- 单元/组件、API、E2E 和安全检查结果；
- 测试数据准备、清理、环境、日志和失败重现信息；
- 说明书、变更说明、接口契约和实际行为是否一致；
- 状态改变前后不变量、偏离项、已知风险和制品摘要。

Gate B 通过后，DevOps 预设逻辑自动创建 PR。缺口路由保持清晰：代码、单元/组件测试和编译参数回 IDE agent；说明书、变更说明、接口契约、API/E2E 测试和测试数据回 DevOps agent。

### Gate C：发布签发

人类审查系统方案中的最终提交、制品摘要、配置、应用方案集合、迁移顺序、健康检查、回滚方式、目标环境和操作范围。Gate C 通过后，IDE agent 只提交发布请求，IDE 预设逻辑执行发布。

## 5. 证据、版本和失败安全

### 5.1 证据绑定

证据至少绑定以下信息：

```text
方案版本、源提交、目标分支、依赖树哈希、配置版本
Runner 身份、工具版本、策略版本、目标环境、制品摘要
测试命令、测试数据、日志、状态改变前后摘要和操作 ID
```

以下任一项变化都会使相关批准和证据变为 `STALE` 或 `REVERIFY_REQUIRED`：方案、提交、PR 差异、依赖、配置、工具、策略、Runner、环境、制品、迁移内容、权限范围或验证命令。

测试报告必须区分“已生成”“已登记”“已执行”“已通过”。覆盖率、稳定性和 AI 解释只能作为信号，不能单独放行。

### 5.2 应用数据状态改变

任何写入、更新、删除、迁移、配置或权限改变都必须满足：

- 对象和允许范围已写入应用方案；
- 执行身份、环境、权限、幂等键和事务边界可验证；
- 执行后不变量、验收用例和审计记录可复核；
- 失败时有已批准的回滚或前向修复。

点方案不能直接改变数据状态。应用方案不能绕过人工确认进入目标环境。系统方案不能绕过 IDE 预设逻辑发布。

### 5.3 失败关闭和未知结果

程序校验、状态机、指纹、权限、审计链或交接控制失败时进入 `FAIL_CLOSED`：冻结待处理动作，使未完成审批失效，禁止创建 PR、合并和发布，并保留故障审计和恢复上下文。

部署或测试结果不明确时进入 `UNKNOWN`。必须使用操作 ID、实际版本和环境状态完成对账，不能把未知结果直接当成功或失败，也不能盲目重试。只有人类确认恢复路径后，程序才可进入 `HUMAN_RECOVERY`。

## 6. 生产热修复和功能线回合并

热修复必须从当前已部署且已核验的生产提交开始，修复完成后再回到仍在开发的功能线。

1. 人类提交生产事件或缺陷 intent，DevOps agent 整理点方案、影响范围、风险和最小修复建议。
2. DevOps 预设逻辑锁定 `prod_sha`、实际制品摘要和事件编号，创建热修复线；生产版本无法确认时先对账。
3. DevOps agent 生成热修复应用方案、文档变更、API/E2E 回归用例和恢复条件，人类签发 Gate A。
4. IDE agent 在热修复线上修改代码，执行单元/组件测试并提交编译请求；IDE 预设逻辑生成和登记制品。
5. DevOps agent 执行 API/E2E 回归测试，维护说明书、变更说明和接口契约，汇总完整证据。
6. 人类签发 Gate B，DevOps 预设逻辑创建指向生产线的 PR；人类在 DevOps 中合并。
7. 程序基于合并后的最终提交生成系统方案；人类签发 Gate C。
8. IDE agent 提交发布请求；IDE 预设逻辑执行生产部署、健康检查和回滚，并回传实际版本和操作结果。
9. 生产发布核验通过后，程序创建同步点方案，标记相关功能线为 `SYNC_REQUIRED`。
10. IDE agent 在同步线上将包含热修复的生产提交准备为回合并 PR，处理冲突并更新单元/组件测试；DevOps agent 更新 API/E2E、说明书和变更说明。
11. 程序校验同步血缘和证据，人类审查同步 PR 后合入功能线。同步过程不产生新的生产发布。

如果功能线已取消、采用其他实现或无法安全合并，人类必须关闭同步任务并记录原因。重新创建功能分支时，必须显式引用该热修复。

## 7. 生命周期典型场景

| 场景 | 工作方式 | DevOps 预设逻辑与 agent | IDE 预设逻辑与 agent | 人类决策 |
| --- | --- | --- | --- | --- |
| 新功能 | intent → Gate A → 开发 → API/E2E → Gate B → PR → 组合验证 → Gate C → 发布请求 | 固化目标、分支、证据和 PR；生成文档、接口契约和 API/E2E 并执行验收 | agent 实现代码和单元/组件测试；程序编译、生成制品、部署和核验 | 确认目标、验收、合并和发布 |
| 预生产缺陷 | 从功能线当前提交修复并补回归证据 | agent 归纳复现条件、变更说明和 API/E2E 回归；程序检查基线和新证据 | agent 修复代码并测试；程序编译和交付候选 | 判断是否扩大范围或阻止合并 |
| 生产热修复 | 从 `prod_sha` 修复、发布，再同步回功能线 | 程序校验生产血缘；agent 维护文档、API/E2E 和同步说明 | agent 修复和准备同步 PR；程序编译、发布、健康检查和回滚 | 确认紧急性、三道 Gate 并合入同步 PR |
| 安全漏洞或依赖升级 | 根据影响版本选择功能线或热修复线 | agent 分析影响、残余风险、文档和回归测试；程序校验依赖锁定 | agent 升级依赖和测试；程序生成制品并发布 | 接受风险或决定升级范围 |
| 配置、特性开关或权限变更 | 应用方案定义具体状态改变和回滚值 | agent 生成说明、接口和 API/E2E 验证；程序校验环境、角色和审计 | agent 提交代码或配置请求；程序执行受控构建和发布 | 确认环境、暴露范围和回滚 |
| 数据库迁移 | 应用方案定义迁移、不变量、兼容和恢复 | agent 维护迁移说明和 API/E2E；程序要求备份、演练和恢复证据 | agent 编写迁移和测试；程序编译、制品和发布 | 承担数据风险并确认恢复路径 |
| 多 PR 集成 | 人类选择 PR，程序以最终组合提交重新验证 | agent 解释冲突、依赖和 API/E2E 失败；程序检查保护规则和组合证据 | agent 解决代码冲突并补测试；程序重新编译和登记制品 | 决定纳入哪些 PR |
| 需求变更或范围扩大 | 旧确认工作区失效，重新生成目标和证据 | agent 对比新旧目标、文档和测试；程序撤销旧批准 | agent 根据新工作区调整代码和单元/组件测试；程序重新编译 | 接受范围、成本和回归风险 |
| 发布失败或未知结果 | 进入 `FAILED`/`UNKNOWN`，对账后恢复 | agent 分析日志、健康结果和候选处置；程序禁止盲目重试 | agent 提交回滚或前向修复请求；程序执行恢复 | 决定恢复路径和是否暂停后续动作 |
| 发布后事件与复盘 | 保留实际版本和证据，必要时转热修复 | agent 汇总影响、原因、文档、API/E2E 和改进建议 | agent 复现、修复和测试；程序编译和发布 | 确认优先级、影响和后续措施 |

所有场景都遵循四条规则：先确定基线；状态改变必须引用应用方案；文档和 API/E2E 由 DevOps agent 维护；编译和发布由 IDE 预设逻辑执行。

## 8. 轻量控制和度量

首期只组合现有 Git、CI、制品库、密钥系统、测试 Runner 和审计能力，不建设多智能体编排平台。

必须保留的控制：

1. 一份权威版本，AI 视图和人类视图不能分叉；
2. Gate A/B/C 绑定指纹，来源变化自动失效；
3. 测试、构建和发布使用最小权限和短时身份；
4. 构建一次、发布同一制品，发布前再次核对摘要；
5. 多 PR 合并后以最终提交重新验证；
6. Prompt Injection、敏感数据出站和越权工具调用必须拦截并审计；
7. 失败关闭、未知结果对账、状态改变幂等且可恢复；
8. IDE 预设逻辑回传实际版本和健康结果，程序阻止版本不一致的后续动作。

建议自动记录以下轻量指标：验收标准返工率、人工驳回率、每个 intent 的修正次数、API/E2E 可复核执行比例、最终组合失败率、变更失败率、恢复成功率、缺陷逃逸、不稳定测试比例、制品摘要一致率、风险提示命中率和策略拒绝次数。

出现以下情况时暂停自动动作并回到人工流程：过期批准未被阻断；证据无法复核；agent 可读取长期生产凭证；Prompt Injection 改变环境或权限；组合验证失败仍可发布；实际版本与签发版本不一致；迁移、失败部署或未知结果无法恢复。

## 9. 首期边界

首期不建设 DevOps 内置代码编辑器、调试器、开发任务编排、第二套 AI 开发 agent、自动合并、无人值守高风险发布、多仓库依赖图、复杂多智能体协作或通用工具市场。

开发步骤、提示词、调试策略、代码组织和单元/组件级测试属于 IDE 侧工具及团队工程规范。说明书、变更说明、接口契约、API 测试和 E2E 测试属于 DevOps agent；其执行必须通过程序允许的隔离 Runner。编译、制品、部署、发布、健康检查和回滚属于 IDE 预设逻辑；IDE agent 只提交请求、读取结果和修复实现。

## 10. 方法论落点

以 intent 为唯一入口，以确认工作区为人机交接，以证据和程序门禁控制流转：点方案只读地说明观察目标并承载建议与参考，应用方案约束软件应用数据状态改变，系统方案提供组合交付输入；DevOps agent 负责文档和 API/E2E 验收，IDE agent 负责开发和请求，IDE 预设逻辑严格控制编译与发布，人类确认、签发、合并并承担最终责任。

从 intent 到发布，五个角色各司其职

把 AI 放进软件工程之后，最重要的不是增加更多 agent，而是让每个角色只做自己能被验证、能被追责的事情。

一句话：人类决定是否继续，程序决定能否继续，agent 负责把工作做出来。

01 / 先记住分工

两条确定性边界，隔开两类 AI 工作

DevOps 管“目标与验收”，IDE 管“代码与发布”。两个 agent 都不能越过程序控制面。

DEVOPS 程序

交接与治理

把 intent 固化为确认工作区，校验版本、权限、证据、分支血缘和 PR 状态。

DEVOPS AGENT

理解与验收

把需求变成方案、说明书、变更说明、接口契约和 API/E2E 测试。

人类

承担判断

确认改变什么，审查证据是否足够，在 Gate A/B/C 做出放行或回退决定。

IDE 程序

工程执行与发布

固定编译器、依赖、构建和制品流程；校验发布输入，执行部署、健康检查和回滚。

IDE AGENT

开发与请求

实现代码、运行单元/组件测试、修复问题，然后提交编译或发布请求并读取结果。

02 / 大家最关心的玩法

同一套协同规则，覆盖常见软件工程场景

变化的是基线和证据，不变化的是五个角色的权责边界。

01

新功能

intent → Gate A → IDE 开发 → DevOps API/E2E → Gate B → PR → Gate C → 发布。

02

生产热修复

从已部署的 prod_sha 修复、发布，再把生产修复回合并到功能线。

03

多个 PR 集成

人类选择纳入范围，程序以最终组合提交重新验证，单个 PR 通过不等于组合通过。

04

说明书与 API/E2E

DevOps agent 负责生成、维护、执行和留存；IDE agent 只负责代码和单元/组件测试。

05

发布失败或结果不明

IDE 程序先进入 FAILED 或 UNKNOWN，通过操作 ID 和实际环境对账；人类决定回滚还是前向修复。

04 / 典型场景：生产热修复

从生产版本修，修完必须回到功能线

热修复不是一条绕过流程的捷径，而是换了基线的同一套流程。

05 / 典型场景：文档与测试

DevOps agent 把“能不能验收”说清楚

IDE agent 聚焦实现；DevOps agent 聚焦外部行为、用户路径和交付说明。

DevOps agent

  • 说明书和变更说明
  • 接口契约与验收标准
  • API 测试与测试数据
  • E2E 测试与用户路径
  • 执行、日志、失败重现和证据汇总

IDE agent

  • 业务代码和代码差异
  • 单元测试与组件测试
  • 实现问题修复
  • 编译/发布请求参数
  • 读取程序结果并回传事实

程序与人类

  • 程序校验版本、权限和 Runner
  • 程序区分生成、登记、执行、通过
  • 人类审查行为是否符合目标
  • 人类决定例外和风险承担
  • 证据变化后批准自动失效
一个常见问题

“代码通过了，为什么还不能发？”

因为代码测试只证明实现局部可用。还要确认接口行为、真实用户路径、文档、测试数据清理、制品来源和目标环境。

一个清晰回答

“谁来补 API/E2E？”

DevOps agent 负责生成、维护、执行和留存；IDE agent 配合提供代码变化和可运行入口，但不接管验收职责。

06 / 典型场景：发布与恢复

agent 可以请求发布，但不能自己发布

编译、制品、部署、健康检查和回滚全部落在 IDE 预设逻辑；DevOps 不调用基础设施 API。

IDE AGENT

提交发布请求

带上确认工作区、系统方案、提交、制品摘要和目标环境。

→
IDE 程序

校验并执行

核对权限、制品、配置和顺序；执行部署、健康检查和回滚。

→
实际结果

回传并记录

记录实际版本、操作 ID、健康结果；版本不一致时阻断后续动作。

FAIL_CLOSED

控制程序故障、权限解析失败或审计链断裂：冻结后续动作。

UNKNOWN

结果不明确：先用操作 ID 和环境状态对账，不得盲目重试。

HUMAN_RECOVERY

人类决定回滚、前向修复或关闭任务，程序负责恢复边界。

发布是一个程序控制的动作，不是 agent 的自然语言承诺。
07 / 只保留最小交接语义

三类方案不增加流程，只说明三件事

用最少的概念把“看什么、改什么、怎么交付”分开，避免职责重叠。

点方案

看什么

只读目标、范围、风险、建议和参考。它不能改变应用数据状态。

应用方案

改什么

明确写入、更新、删除、迁移、配置或权限改变，以及验收和回滚。

系统方案

怎么交付

组合最终提交、制品、配置、环境、顺序、健康检查和恢复方式，作为 IDE 程序的发布输入。

08 / 协同规则

三句话，管住五个角色

生成不等于授权。
agent 可以提出方案、代码、测试和发布请求。
程序决定能否继续。
版本、权限、证据、编译、制品和发布条件必须可判定。
人类承担结果。
人类确认目标、签发交付、合并 PR，并处理例外和未知状态。

最终的工作方式

以 intent 为入口，以确认工作区为交接，以证据门禁控制流转。DevOps agent 负责文档和 API/E2E 验收，IDE agent 负责开发和请求，IDE 程序严格控制编译与发布，DevOps 程序严格控制状态与权限，人类在关键节点做出判断。

09 / 结论

轻量，不等于少控制

小团队只需要把控制放在最关键的边界：目标确认、证据验收、组合合并和程序化发布。

保留

确定性控制

版本、权限、证据、分支、编译、制品、部署和回滚。

授权

受控 AI 协作

让两个 agent 承担整理、实现和验收工作，但不给它们最终放行权。

聚焦

人的判断

把人的时间放在目标、风险、证据和例外，而不是重复搬运信息。

适合小团队的最小闭环：目标清楚、证据完整、程序可控、人类负责。
